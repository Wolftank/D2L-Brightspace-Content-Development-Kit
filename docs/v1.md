# V1

Terms are defined in [architecture.md](architecture.md#terms). V1 is the smallest slice of that design that works end to end, built in Sprint 1 and finished in Sprint 2 at the latest. Everything later is added on top of it, never in place of it.

## Goal

An instructor types what they want, clicks Build, and gets a SCORM package that passes the QA gate and uploads to D2L. Local mode, run from source on a Windows laptop, Claude as the agent.

## Done means

1. Start the back end and the front end from source; the browser opens the page.
2. Type a request such as "a ten-question multiple-choice practice set on cell division that students can retake, with the score in the gradebook" and click Build.
3. Status lines appear while the agent works. When the turn ends, a build appears with the QA gate result and a Download button.
4. Upload the zip to the sandbox course, launch it as a student, finish it, and see the score in the gradebook.

Step 4 is manual and is the test that matters.

## What V1 leaves out

| Left out | Why | Added by layer |
|---|---|---|
| Choosing an avenue | The output is a SCORM package because it is a self-contained file, the kit has a starter, QA gate rules, and an emulator for it, and deployment can be a manual upload | 6 |
| Chat history in the UI | One message per project is enough to produce a build. The API is the full chat API; the UI shows one text box and the status | 1 |
| Tools for the agent | The agent runs the QA gate through the shell during its turn, as the skills already instruct, and the runner creates the build at turn end. Structured findings and a preview come with the tools | 2 |
| Preview | Needs the emulator wired into the front end | 3 |
| Pedagogy check | Needs its own implementation | 4 |
| Deployment through the D2L API | The highest-uncertainty piece; the zip is uploaded by hand | 5 |
| Cancel, and limits on a turn | V1 imposes no step, spending, or time limit. A stuck turn holds its project until the back end restarts, which fails it as `interrupted` | 1 |
| Launch token | Binding to 127.0.0.1 is enough while the app runs from source on a developer's laptop | 7 |
| Packaging as a Windows app | Runs from source | 7 |
| Copilot | One driver proves the interface | 8 |
| Hosted mode | Identity is the stub user | 9 |

## The path

1. The UI posts `POST /api/projects { title, avenue: 'scorm' }`, then `POST /api/projects/:id/messages` with the instructor's text, and opens the event stream.
2. The workspace service creates the workspace with the SCORM starter in `out/`. When the runner opens the session, the Claude driver writes the instructions as `CLAUDE.md` (the project title, the avenue, the tenant profile, and the rules: build in `out/`, run the QA gate before finishing, keep the UI under 600px, never mark completed on load), copies the kit's skills into `.claude/skills/`, and writes its permission rules to `.claude/settings.json`.
3. The runner opens a session through the Claude driver and sends the message with no limits.
4. The driver maps the agent's stream to events: text deltas become `message.delta`, tool calls become `tool.started` and `tool.finished` with a plain-language summary, and the turn ends with the agent's message stored and `message.completed`.
5. The runner compares the hash of `out/` with the turn's start, since the project has no build yet. It changed, so the runner creates a build: copies `out/` to `builds/1/`, runs `node kit/harness/lint/lint.js builds/1 --avenue scorm --json` as a child process, stores the result as `qa.json`, and emits `build.created` and `build.updated`. Then it emits `turn.completed`.
6. The UI shows the build with the QA gate result and a Download button. `GET /api/builds/:id/download` zips the build with `imsmanifest.xml` at the zip root, after checking that every file the manifest declares exists. This replaces the kit's former `build-scorm.ps1` packaging script.

## The API V1 implements

```
POST   /api/projects
GET    /api/projects/:projectId
POST   /api/projects/:projectId/messages
GET    /api/projects/:projectId/events
GET    /api/builds/:buildId
GET    /api/builds/:buildId/download
```

Resources used: User (one stub row), Project, Message, Turn, Build, Event, all in SQLite from the first commit. Events emitted: `turn.started`, `turn.status`, `message.delta`, `message.completed`, `tool.started`, `tool.finished`, `build.created`, `build.updated`, `turn.completed`, `turn.failed`, `turn.cancelled`. Shapes are exactly those in [architecture.md](architecture.md); V1 implements a subset of routes, not simplified versions of them.

## What each track builds

**Back end, Sprint 1.** SQLite schema and repositories. Project creation, with the workspace service provisioning the workspace. The Claude driver: `open`, `send`, `close`, event mapping, session id capture. The runner: one turn at a time, events written then pushed, the build at turn end, the QA gate as a child process. Routes for the six endpoints. By the end of the sprint the whole path runs from a REST client without a UI.

**Front end, Sprint 1.** The page: title, text box, Build button, a status feed fed by `EventSource`, and a build card with the QA gate findings and the Download button. Findings are shown as the QA gate reports them; plain-language rewording is a later layer. Built against the contract in [architecture.md](architecture.md) with a stub server until the back end lands.

**Quality and adoption, Sprint 1.** The demo script above, run against the sandbox course with a real student enrollment, which the SCORM skill says is the only way to verify a package. The first draft of the instructions, taken from the kit's skills.

**Sprint 2.** Integration, error handling (a failed turn, a QA gate failure, a missing sign-in reported through `GET /api/me`), the retry path when the QA gate fails (the instructor sends a second message, which is layer 1's first step), and the demo.

## Unknowns to retire in the first week

1. The Claude SDK from a Node process on Windows: cold-start time, that `settingSources: ['project']` loads the copied skills, that `permissionMode: 'dontAsk'` plus the workspace rules confine edits to the workspace, and that the session id is captured from the first message.
2. That a zip built in Node with the manifest at the root is accepted by the sandbox course.
3. That the QA gate's `--json` output is stable enough to store as `qa.json` and render.

## The layers after V1

1. **Chat.** Message history in the UI, cancel and turn limits, the launch token.
2. **Tools.** `create_build` and `get_build` so the agent gets structured findings and iterates within a turn; `get_project`.
3. **Preview.** The emulator wired into the build panel.
4. **Pedagogy check.** `POST /api/builds/:id/pedagogy`, `POST /api/checks/pedagogy`, and the `check_pedagogy` tool.
5. **Deployment.** `propose_deploy`, the human gate, and the D2L client.
6. **Avenues.** The router skill decides the avenue; the topic, widget, and external avenues.
7. **Local mode as a product.** Packaging as a Windows app, the launch token, the instructor's own agent sign-in surfaced in the UI.
8. **Copilot.** The second driver, with its gaps recorded in [drivers.md](drivers.md).
9. **Hosted mode.** OIDC identity, per-instructor workspaces, the OS sandbox, caps.
