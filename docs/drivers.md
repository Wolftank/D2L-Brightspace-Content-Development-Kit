# Drivers

Terms are defined in [architecture.md](architecture.md#terms). This file records what was verified about each agent, from its official documentation, so each driver is designed from facts rather than assumptions. Anything marked *unverified* was not found in the documentation read on 2026-09-10 and must be checked before it is relied on. Codex was evaluated for comparison and is not planned.

## Claude

**Running a turn.** `query({ prompt, options })` returns an async iterable of messages. `options.cwd` sets the workspace. `options.resume` reopens a session by id; `options.continue` reopens the most recent one; `options.forkSession` branches. The session id is on the first message, `type: 'system', subtype: 'init'`, and on the final `result` message, which also carries `subtype` (`success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`), `usage`, `total_cost_usd`, and `num_turns`. With `includePartialMessages: true` the stream includes `stream_event` messages carrying text deltas.

**Keeping a session open.** The prompt may be an async iterable of user messages instead of a string. The query then stays alive across several instructor messages, which the SDK documents as the mode to use for chat. This is what lets the Claude driver keep a process alive inside an open session and drop it on idle timeout. Confirmed 2026-09-15: feeding two user messages through one kept-open async-iterable prompt (a 4s gap between them) produced exactly one `result` message per instructor message, `subtype: 'success'` each time, with the same `session_id` throughout. A `system`/`init` message was also re-emitted before the second turn (same `session_id`) — the driver should key turn boundaries off `result`, not assume `init` arrives only once.

**Tools.** `createSdkMcpServer({ name, tools: [tool(name, description, zodSchema, handler)] })`, passed as `options.mcpServers`. The agent sees each as `mcp__<server>__<tool>`, and each must be listed in `options.allowedTools`.

**Permissions.** `permissionMode: 'dontAsk'` denies anything not pre-approved without prompting; `acceptEdits` auto-approves edits and common filesystem commands inside the workspace only. Rules live in the workspace's `.claude/settings.json` under `permissions.allow`, `deny`, and `ask`, with the syntax `Read(pattern)`, `Edit(pattern)`, `Write(pattern)`, `Bash(prefix *)`; `//` is an absolute path, `/` is workspace-relative, `~/` is home. `settingSources: ['project']` loads that file and the workspace's `.claude/skills/`. `permissions.additionalDirectories` widens file access without loading configuration from those directories.

**Permissions, confirmed 2026-09-15.** More subtle than the above implies. Under `dontAsk`, `Read` is auto-approved straight from `.claude/settings.json`'s `permissions.allow` (e.g. `Read(/**)`) with nothing extra needed in `options.allowedTools`. `Edit`, `Write`, and `Bash` are *not* auto-approved from `settings.json` alone: even with a matching `allow` rule on disk, a call to one of them was denied outright unless the identical scoped pattern (`Edit(/**)`, `Write(/**)`, `Bash(node *)`) was *also* passed in `options.allowedTools` — a driver must mirror every mutating-tool rule into both places, not just settings. Separately, a bare/unscoped tool name in `options.allowedTools` (`'Read'` instead of `'Read(/**)'`) grants that tool blanket approval and silently overrides `settings.json`'s path-scoped rules, deny rules included — verified by denying a specific out-of-workspace file, then watching `allowedTools: ['Read']` read it anyway; with the bare name removed and `'Read(/**)'` used instead, the same file was correctly denied. A driver must never place unscoped built-in tool names in `allowedTools`. Every no-prompt denial arrives as `{ type: 'system', subtype: 'permission_denied', tool_name, decision_reason_type: 'mode', message }`, confirmed for `Read`, `Edit`, `Write`, `Bash`, and `PowerShell` — each denial was a single round trip with no interactive prompt of any kind. One caveat worth flagging for #25: the `Bash` tool appears to auto-approve a small set of recognized read-only commands (observed: `git status`) even when they match no `Bash(...)` allow pattern, as long as *some* `Bash` allow rule exists at all; with no `Bash` rule present anywhere (settings or `allowedTools`), even those commands were denied outright, same as a `curl` network call. This exemption isn't in the SDK's type reference and shouldn't be assumed for confinement — a kit tool server that truly needs to forbid all shell access should omit every `Bash` rule, not rely on a narrow allow pattern to keep other commands out.

**Permissions, addendum 2026-09-17.** The 2026-09-15 finding above was accurate for whatever SDK version that spike (issue #24) ran against, but is not stable across versions: on `@anthropic-ai/claude-agent-sdk` **0.3.274**, a bare `Bash` call with zero `Bash` rules anywhere (neither `settings.json` nor `options.allowedTools`) was **not** denied by the SDK itself — `git status` executed and only failed because the workspace wasn't a git repository, same as running it from an ordinary shell. The CLI 2.1.274 source (read 2026-09-25) explains it: the `Bash` and `PowerShell` tools approve commands they recognize as read-only on their own, in `dontAsk` too, with no rule anywhere. Package.json now pins `@anthropic-ai/claude-agent-sdk` to an exact version rather than a range, so this can't silently drift again without a deliberate bump.

**Shell, read from the CLI 2.1.274 source, 2026-09-25.** The driver allows every command in the agent's shell by listing the bare tool name in `options.allowedTools`; `Bash(*)` parses to the same rule. That is the one exception to the bare-name rule above, because shell rules never widen the file tools and there are no path-scoped shell rules to override. Even with every command allowed, `dontAsk` still denies a matching deny or ask rule and the CLI's own safety checks, which differ by shell. Bash's include `rm` of the workspace, its parents, critical system paths, or a target it cannot resolve in advance, and writes to sensitive targets such as `.claude/`, `.git`, shell startup files, `.npmrc`, and `.mcp.json`, checked in every part of a compound command. PowerShell's are weaker: it always denies `Remove-Item` of protected system paths (drive roots, the home directory), but denies a write to a sensitive target only when that is the first objection it finds in the command, and `Remove-Item -Recurse` of the workspace or its parents runs. Outside those checks, commands run, including network commands, command substitution, and reads and writes outside the workspace, because `Read(/**)` and `Edit(/**)` bind the file tools, not shell commands. Narrower rules are fragile: `Bash(node *)` matches the literal command text, quoting included, part by part through a compound command, and is no boundary anyway, because `node -e` runs anything. On Windows the CLI offers Bash whenever it finds Git for Windows, and PowerShell when `CLAUDE_CODE_USE_POWERSHELL_TOOL` is true, when Git is missing, or when a server-side account flag is on (off by default); with both, the agent picks. The driver pins PowerShell there, so instructors need no Git: `options.env` sets `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` over a copy of `process.env`, because the option replaces the environment rather than adding to it, and `disallowedTools: ['Bash']` withholds Bash. Disallowing Bash without enabling PowerShell leaves the agent no shell at all. With Git for Windows present, the CLI's environment note to the model still says a Bash tool is available; a Bash call then fails as an unknown tool and costs a step. The CLI labels its PowerShell tool preview, and it runs Windows PowerShell 5.1 when PowerShell 7 is not installed. Shell commands inherit the back end's environment, including any API key in it.

**Instructions and skills.** Claude reads `CLAUDE.md`, `.claude/skills/`, and `.claude/settings.json` from the workspace when `settingSources: ['project']` is set, so the driver writes the instructions, a copy of the kit's skills, and the permission rules there at every `open`.

**Hooks.** `options.hooks.PreToolUse` and `PostToolUse` are in-process callbacks. A pre-tool hook denies a call by returning `hookSpecificOutput.permissionDecision: 'deny'` with a `permissionDecisionReason`. This is layer 3 of the confinement.

**Sandbox.** `sandbox.enabled` in settings confines shell writes to the workspace and blocks network access except `sandbox.network.allowedDomains`; `sandbox.failIfUnavailable` makes an unsupported host refuse to run. Supported on macOS, Linux, and WSL2, not on native Windows.

**Limits.** `maxTurns` and `maxBudgetUsd` are enforced by the SDK, and the SDK leaves out the matching CLI flag when either is undefined, so an omitted `TurnLimits` field imposes no limit. There is no wall-clock option; a caller that wants one fires the turn's abort signal.

**Failures and summaries.** A result the provider marked as an error (`subtype: 'success'` with `is_error: true`, such as a rate limit or an expired sign-in) is a failed turn, not a completed one. The driver codes it from the `error` on the turn's assistant messages: `authentication_failed`, `oauth_org_not_allowed`, and `verification_required` are `agent_signed_out`, `billing_error` and `account_on_hold` are `agent_billing`, `rate_limit` and `overloaded` are `agent_busy`, and anything else is `agent_error`. Each `tool_start` event carries a plain-language `summary` built from Claude's tool name and input: the shell command's own `description`, "Reading", "Writing", or "Editing" plus the file's name, "Searching the files" for Glob and Grep, and "Using <name>" for any other tool.

**Cancellation, confirmed 2026-09-15.** Passing `options.abortController` and calling `.abort()` mid-turn does stop the turn: consuming `query()`'s async iterable throws a plain `Error` (message `'Operation aborted'` — not a `DOMException`/`AbortError`, no `.code`) once the abort is fully processed. A handful of already-in-flight low-level events (`stream_event` deltas, `rate_limit_event`, `system`/`thinking_tokens` telemetry) can still surface after `.abort()` is called and before that exception; none of them were a new `tool_use`, and a turn aborted immediately after starting (writing a long file) left no partial file on disk. A driver's turn-consumption loop needs a `try/catch` around its `for await` and should treat this exception (or a check of `abortController.signal.aborted`) as `TurnResult.status: 'cancelled'`, not `'failed'`.

**Timing, measured 2026-09-15.** Wall-clock from calling `query()` to the first `stream_event` text delta, on this machine: **cold** (first `query()` call in a fresh `node` process) **~8.9–10.6s** across two clean runs; **warm** (second `query()` call in the same process, via `resume`) **~1.5–2.2s**. A third cold run measured 38.8s, but that run's `allowedTools` was misconfigured so the agent's first two tool calls (`Edit`, `Write`) were denied and it re-planned before any text streamed — that number reflects extra permission round-trips, not cold-start cost, and is excluded from the range above.

**State.** Transcripts are stored per workspace under the configuration directory and pruned after `cleanupPeriodDays`. `CLAUDE_CONFIG_DIR` relocates transcripts, settings, and sign-in together.

**Windows.** The SDK bundles the binary. The agent's shell is PowerShell, pinned by the driver (see "Shell").

**Gaps.** No OS sandbox on native Windows, so local mode on Windows runs layers 1 to 3 only. The turn boundary inside a kept-open query — a `result` message per instructor message — is confirmed (see "Keeping a session open"). Remaining open question after the first spike (issue #24): the exact behavior of `permissions.additionalDirectories`, which this spike did not exercise.

## Copilot

**Running the agent.** `new CopilotClient({ cwd, cliPath?, cliUrl?, env?, autoStart, autoRestart, useStdio })` spawns the CLI as a server and manages its lifetime; `cliUrl` attaches to one already running. The workspace is set on the client, not the session, so the driver holds one client per workspace and one session inside it.

**Sessions.** `client.createSession({ sessionId, model, tools, mcpServers, systemMessage, streaming, onPermissionRequest, availableTools, excludedTools })`. The caller chooses `sessionId`, so the driver can use the project id and the Project's `sessionId` is deterministic. `client.resumeSession(id, { onPermissionRequest })` reopens a session, including after the client and CLI have restarted; the full message thread, cached tool results, and the agent's planning state are restored, and tools keep their registration but not their in-memory state. `listSessions()`, `deleteSession(id)`, and `disconnect()` (release memory, keep disk state) exist. State lives in `~/.copilot/session-state/<id>/`.

**Turns.** `session.send({ prompt })` returns when the message is accepted; `session.sendAndWait({ prompt })` returns the final `assistant.message`. Events via `session.on(kind, handler)`: `assistant.message_delta` with `data.deltaContent`, `assistant.message` with `data.content`, `tool.executionStart`, `tool.executionComplete`, `session.idle` when the turn is done, `session.error`. `session.abort()` stops a running turn; `session.destroy()` tears it down.

**Tools.** `defineTool(name, { description, parameters, handler })` with parameters as JSON Schema or a zod schema; handlers return a value or `{ textResultForLlm, resultType, error? }`. MCP servers are passed per session as `{ type: 'stdio' | 'local', command, args, env?, cwd?, tools? }` or `{ type: 'http' | 'sse', url, headers?, tools? }`, with a `tools` array to select which of a server's tools are exposed.

**Instructions and skills.** The SDK takes instructions as `systemMessage` and loads skills only from the directories listed in `skillDirectories`; it does not discover `.github/skills`, `.claude/skills`, or `.agents/skills` in the workspace. The driver therefore points `skillDirectories` at the kit and writes nothing into the workspace. The CLI on its own behaves differently: it reads `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, and `.github/instructions/*.instructions.md` from the working directory and discovers skills in all three project locations.

**Permissions.** `onPermissionRequest` is required on every session. The SDK ships an `approveAll` helper, which this project never uses; the driver's handler allows the allowlist and denies everything else. The GA release notes list hooks at pre and post tool use, session start, MCP tool calls, and permission requests.

**Sandbox.** Local sandboxing is experimental, enabled per session with `/sandbox enable` behind the `--experimental` flag, configured under the `sandbox` key of `settings.json`. It isolates shell commands, file search, and optionally MCP and language servers, using Seatbelt on macOS 15+, bubblewrap on Linux, and a process container on recent Windows 11 builds. The CLI's own built-in file tools run in-process and are not covered by it.

**CLI without the SDK.** `copilot -p "prompt"` runs one prompt and exits, with `--allow-tool`, `--deny-tool`, `--allow-all-tools`, `--add-dir`, `--allow-all-paths`, `--model`, `--no-ask-user`, and `-s` for bare output. Tool kinds are `shell`, `write`, `read`, `url`, `memory`, and MCP server names, each with a filter such as `shell(git:*)`. No machine-readable output mode is documented for the CLI, which is why the driver uses the SDK.

**State.** `COPILOT_HOME` relocates the configuration directory, which holds `config.json` (with `trustedFolders`), `settings.json`, and `session-state/`.

**Gaps and unverified points.** The custom decision shape returned by `onPermissionRequest` beyond `approveAll`. The signature of pre-tool hooks and whether one can deny a call, which layer 3 depends on. Per-turn limits equivalent to `maxTurns` and `maxBudgetUsd`. Whether the CLI process the SDK spawns also reads instruction files from the workspace, which would matter only when a `CLAUDE.md` written by the Claude driver is still present after an install switched agents. Sandbox support on the Windows builds instructors actually run. Billing and model availability on a shared service account in hosted mode.

## Codex, for comparison

`codex.startThread({ workingDirectory, skipGitRepoCheck })` and `codex.resumeThread(threadId)`; `thread.run(prompt)` or `thread.runStreamed(prompt)`, which the SDK executes by spawning the CLI and exchanging JSONL over stdio. The CLI equivalent is `codex exec --json`, whose first event is `thread.started` with `thread_id`, and `codex exec resume <id>`. Threads persist under `~/.codex/sessions`. The sandbox modes are `read-only`, `workspace-write` (network off unless `[sandbox_workspace_write] network_access = true`), and `danger-full-access`; approvals are `on-request` or `never`. The sandbox uses Seatbelt on macOS, bubblewrap with seccomp on Linux, and a native implementation on Windows, with WSL2 inheriting the Linux one. MCP servers are registered in `~/.codex/config.toml` under `[mcp_servers]` or with `codex mcp add`. Its native Windows sandbox is the one capability the two planned agents lack in local mode.
