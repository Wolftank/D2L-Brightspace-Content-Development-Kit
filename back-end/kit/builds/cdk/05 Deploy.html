Step Five

Deploy

Set expectations

This is not one button

Deploying is five stages, and they have to happen in order. Two of them are effectively permanent, and one of them cannot be done from your own account at all.

None of that is difficult. It is just genuinely worth reading before you begin rather than discovering halfway through.

The stages

in order, no skipping
1

Name it, and mean it

The file name becomes the topic title students see. Renaming a live topic re-saves the page and silently destroys anything interactive in it. So does opening it in D2L's built-in HTML editor, even if you cancel.

Get the wording right now. This is the single most common way a working activity becomes a blank one.

2

Upload

Where you go depends on what you built.

A content topic goes in through the Lessons drop zone, which uploads the file and creates the topic in one move:

Content → a unit → Add Existing → drop the file

If your build has sibling files (a data.js, an image), dropping all of them together uploads every file to the same folder correctly, but D2L also creates one visible topic per file, not one topic with hidden assets. Upload just the .html first, then push the siblings in separately through Manage Files. If you already dropped everything at once, delete each extra topic entry via its ··· → Delete → "Remove the topic from Content but keep the associated file" — the default option, and the one that keeps your real topic's sibling-file references working.

A SCORM package has its own path, and it is not where most people look first. It is not in Course Admin:

Content → a unit → Add Existing → SCORM/xAPI Object → Bulk Upload

Claude can drive either of these for you if you would rather not click. Ask it to deploy the build and tell it which course.

3

Configure, while it is asking

A SCORM package asks a few questions as you add it, and these are much easier to set now than to change later.

  • Create a grade item? Usually yes. This is what makes the score land somewhere.
  • Grade calculation method. Highest Attempt is the default and is usually what people mean by "best of three". Lowest, Average, First and Last are all there too.
  • Player. Embedded looks tidier. Choose new window if your activity is tall, because the embedded player will not scroll.

You do not have to build attempt limits or best-of-N yourself. It is a setting.

4

Verify as a student, because you cannot verify as yourself

For a SCORM package this is not a nicety. When you open your own package, D2L gives you a preview that throws away every score and every saved answer, and reports no error while doing it. Everything will look like it worked. Nothing will have been recorded.

Ask a TA, intern, or colleague enrolled as a student to open it once. Check that it opens, that finishing it puts a number in the gradebook, and that a second attempt behaves the way you expect. This is the one thing the emulator cannot do for you, and it takes about five minutes of someone else's time.

For a content topic you can check it yourself, but still confirm that a student sees the student version and not your instructor view.

If it shows different things to different roles, one helper can check all of them. Change their enrolment role, have them reload, and look again. The same person enrolled as a student, then as a TA, exercises every branch you built without involving anyone else.

5

Updating later

For a content topic, upload the changed file again and choose to overwrite. Never rename it while doing so.

For SCORM, upload a new version and then publish it explicitly, which is a separate click:

Add Existing → SCORM/xAPI Object → the package's … menu → Manage Versions

D2L will warn you that publishing updates the package everywhere it is used. If you have put the same activity in several places, they all change at once.

If something looks wrong afterwards

in order of likelihood
  • You tested it yourself. For SCORM that proves nothing. Have someone enrolled as a student open it.
  • The topic was renamed, or opened in the HTML editor. Both silently corrupt it. Not repairable; redeploy a fresh copy.
  • It reports complete immediately. Then every later attempt is read-only and best-of-N has stopped working. Rebuild so completion only happens when the student actually finishes.
  • Progress is not saving. Check whether the activity is trying to store more than about 4000 characters, or whether it is relying on browser storage, which follows the computer rather than the person.

When in doubt, tell Claude what you saw. It has the measured behaviour in front of it and the list of things that fail silently is short.

One last thing

Do it in your own course first

Every one of these stages is reversible in a course of your own and awkward in one students are taking. Build there, deploy there, break it there, and move the finished thing across once you are happy.
